Abstract 
 
“Vibe coding” enables non-technical users and developers to create full-stack web applications by de-
scribing their requirements in natural language to platforms such as Lovable, Bolt, Replit, and Base44. 
Although this approach accelerates software development, it can also result in applications being 
deployed without sufficient security review. Research on AI-generated code has examined security 
weak-nesses in generated contributions and projects, highlighting the importance of reviewing 
generated code before deployment. Common web application security risks include inadequate access 
control, injection vulnerabilities, and security misconfiguration. These risks highlight the need for 
accessible security assessment tools that can evaluate applications created through AI-assisted 
development. 
VibePen is a vulnerability-scanning system designed to assess such applications through two input 
modes: source-code archive analysis and authorized live-website scanning. Its proposed analysis pipeline 
combines static analysis using Semgrep and Tree-sitter with dynamic analysis through a Playwright-based 
crawler. A large language model (LLM) reasoning layer is intended to assess candidate findings, 
correlate evidence across files, and help reduce false positives. The system presents prioritized 
findings in a plain-language report containing supporting evidence and remediation guidance. To reduce 
the risk of unauthorized testing, live scanning is restricted to domains whose ownership has been 
verified through an approved verification mechanism. VibePen is designed to identify and report 
potential vulnerabilities rather than modify the target application. 
This report presents the project background, vision and scope, related tools and research, software 
requirements, system architecture, and detailed design. It establishes the requirements and design 
foundation for implementation and subsequent evaluation using authorized benchmark applications 
and appli-cations generated through AI-assisted development.

Executive Summary 
 
AI-assisted development platforms allow users with limited programming experience to create and de-
ploy web applications rapidly. However, generated code can contain security weaknesses, and conven-
tional web application risks such as inadequate access control, injection, and security misconfiguration 
remain relevant [1, 2]. Conventional security tools can identify many of these issues, but their technical 
output and configuration requirements may make them difficult for non-specialists to use effectively. 
VibePen addresses this problem by providing a security assessment workflow intended for applications 
created through natural-language prompting and AI-generated code. Its goal is to make potential vul-
nerabilities easier to identify, understand, prioritize, and address before they lead to security incidents. 
VibePen is designed to support source-code and live-website scanning. In source-code mode, users 
submit a project archive for analysis without executing the submitted application. In live-website mode, 
users must first demonstrate control of the target domain through an approved verification method. A 
rate-limited crawler then examines the authorized website. Static and dynamic analysis components 
identify candidate vulnerabilities, while an LLM-based reasoning layer evaluates the available evidence 
and helps connect related findings. The system produces a severity-ranked report with explanations, 
evidence, and recommended remediation steps. VibePen is intended to report potential weaknesses 
rather than make changes to the target application, and its findings require appropriate interpretation and 
validation. 
This deliverable defines the requirements and design needed to guide implementation. It covers the 
project background and objectives, related security tools and research, functional and non-functional 
requirements, use cases, interface designs, database structure, system architecture, module interactions, 
API design, and security controls. These elements establish a common specification for development and 
testing. The design also identifies operational constraints and risks, including false positives, incomplete 
scan coverage, external service dependencies, and the need to prevent unauthorized website testing. 
The next project phase will implement the specified components and evaluate their performance against 
authorized benchmark applications. The evaluation is intended to include open-source applications, in-
tentionally vulnerable applications, and applications generated by the project team using AI-assisted 
development tools. The resulting evaluation will examine whether the system identifies relevant weak-
nesses, produces useful evidence, and communicates findings clearly. Implementation details, evaluation 
results, user documentation, and the final project report will establish the extent to which VibePen meets 
its objectives and where further improvements are required.

Chapter 1  Introduction 
 
Vibe coding has made software development significantly more accessible by allowing users to describe 
an application in natural language and obtain a working implementation with limited traditional pro-
gramming knowledge. AI-assisted development platforms such as Lovable, Bolt, Replit, and Base44 
can generate complete web applications within a short period of time. This development approach re-
duces the technical barrier to software creation and enables individuals, students, freelancers, and small 
businesses to build applications without extensive programming experience. However, the speed and 
convenience of AI-generated development can also introduce security risks because generated appli-
cations may be deployed without undergoing a professional security review. Vulnerabilities may ex-
ist in authentication, authorization, database configuration, source code, dependencies, and application 
interfaces. These weaknesses can remain unnoticed when application creators do not have sufficient 
security knowledge. VibePen is proposed as an automated security scanner specifically designed for 
AI-generated web applications. The system combines static source-code analysis, controlled dynamic 
analysis, and an AI-assisted reasoning layer to identify, validate, prioritize, and explain security findings. 
 
1.1 Purpose of this Document 
 
The purpose of this document is to present the problem addressed by VibePen and describe the proposed 
solution, requirements, and design of the system. The document establishes the motivation for devel-
oping a security scanner specifically for applications created through AI-assisted development and ex-
plains the limitations of relying on conventional security tools for this emerging development approach. 
VibePen is intended to accept either a source-code archive or a verified live web application and analyze 
it for common security weaknesses. The document therefore provides the foundation for understand-
ing how the proposed system will operate and why its different components are required. It describes 
the project vision, problem domain, scope, stakeholders, functional and non-functional requirements, 
and high-level and low-level design. The report also establishes the boundaries of the system so that 
development remains focused on vulnerability detection, evidence-based analysis, and understandable 
reporting rather than automatic code modification or unrestricted penetration testing. The document will 
serve as a reference throughout the implementation and evaluation phases of the Final Year Project.

Chapter 2  Project Vision 
 
2.1 Problem Domain Overview 
 
VibePen operates in the domain of web application security, with a specific focus on applications cre-
ated through AI-assisted or “vibe coding” development. These applications are commonly generated by 
describing desired functionality in natural language and allowing an AI coding system to produce the 
required source code. The resulting applications may contain a front-end interface connected to a hosted 
database or Backend-as-a-Service platform such as Supabase or Firebase, with serverless functions pro-
viding additional application logic. Although this approach reduces development effort, the generated 
applications may contain security weaknesses because their creators may not have sufficient knowledge 
to identify insecure implementation choices. Vulnerabilities can occur in source code, authentication 
and authorization mechanisms, dependencies, database access rules, configuration, and interactions be-
tween different components. VibePen addresses this domain by providing automated security analysis 
for both uploaded source code and authorized live applications. Static analysis is used to identify source-
level weaknesses, secrets, insecure patterns, and dependency issues, while dynamic analysis examines 
the behavior of running applications through controlled crawling and harmless test inputs. Findings 
from both approaches are normalized and passed to an AI-assisted reasoning layer that validates evi-
dence, identifies relationships between findings, reduces false positives, and generates understandable 
explanations. 
 
2.2 Problem Statement 
 
Applications generated through AI-assisted development can be deployed without receiving an adequate 
security review. Application owners who rely on AI coding tools may have sufficient knowledge to de-
scribe the desired functionality of an application but may not possess the security expertise required to 
evaluate the generated implementation. As a result, vulnerabilities involving authentication, authoriza-
tion, exposed credentials, database permissions, dependencies, input validation, and configuration may 
remain undetected. Existing security tools can identify many individual classes of vulnerabilities, but 
they are generally designed for professional developers and security specialists. Their output may con-
tain technical terminology, rule identifiers, or other information that is difficult for non-expert users to 
interpret. General-purpose tools also do not necessarily focus on recurring security problems associated 
with AI-generated applications, such as hallucinated dependencies or permissive Backend-as-a-Service 
configurations. Furthermore, relying only on source-code analysis can miss runtime behavior, while 
relying only on dynamic analysis can miss weaknesses that are not reached during testing. There is

therefore a need for a system that combines multiple analysis approaches, focuses on common weak-
nesses of AI-generated applications, validates findings using evidence, and communicates the results in 
a form that application owners can understand and act upon. 
 
2.3 Problem Elaboration 
 
The problem addressed by VibePen consists of several related challenges. AI-generated applications 
may contain predictable security weaknesses that are difficult for non-experts to identify. At the same 
time, individual analysis techniques provide only a partial view of application security. Static analysis 
can inspect source code but cannot directly observe runtime behavior, whereas dynamic analysis can 
observe a running application but cannot reach every possible code path. Another challenge is the 
interpretation of security findings. A technically correct scanner result may still be of limited practical 
value if the user cannot understand its impact or determine how to address it. Finally, live security testing 
introduces authorization and safety concerns because scanning a website without permission may cause 
harm or violate applicable rules. VibePen therefore treats vulnerability detection, evidence validation, 
understandable reporting, and authorized testing as interconnected parts of the same problem rather than 
separate features. 
 
2.3.1 Security Weaknesses Typical of AI-Generated Applications 
 
AI-generated web applications may contain recurring security weaknesses because AI coding systems 
generally optimize for producing functional implementations rather than guaranteeing secure designs. 
VibePen focuses on weaknesses such as exposed credentials in source code or client-side bundles, miss-
ing or weak authentication, broken authorization including Insecure Direct Object References, injection 
vulnerabilities, permissive database and storage rules, insecure configuration, missing security headers, 
overly permissive Cross-Origin Resource Sharing settings, and unsafe or hallucinated dependencies. 
These weaknesses may occur independently or may interact with one another to create a more serious 
security issue. For example, an application can contain an authentication mechanism but still expose 
another user’s information because authorization is not enforced on an individual data-access route. 
Similarly, credentials may be unintentionally included in client-side code even though the application 
appears to provide a secure login mechanism. The scanner must therefore examine more than the visible 
interface and should consider relationships between application components. This requirement moti-
vates the use of multiple analysis techniques and an AI-assisted reasoning layer capable of considering 
evidence from different files and execution paths.

2.3.2 Limits of a Single Analysis Technique 
 
Static analysis provides the ability to inspect source code, configuration files, dependencies, and other 
project artifacts without executing the application. This makes it useful for detecting exposed secrets, 
insecure coding patterns, suspicious dependencies, and configuration weaknesses. However, static anal-
ysis cannot directly determine how an application behaves during execution or whether a particular 
access-control rule is actually enforced at runtime. Dynamic analysis provides the opposite perspective 
by interacting with a running application and observing its responses, headers, network activity, and ac-
cessible functionality. Its limitation is that it can only inspect the application areas reached by the crawler 
and test cases. Some security weaknesses also require information from multiple sources. A route may 
appear protected in isolation while a related route or database policy bypasses the intended authorization 
mechanism. VibePen therefore combines static and dynamic analysis and uses an AI-assisted reasoning 
layer to correlate the resulting evidence. This approach is intended to provide broader coverage while 
allowing the system to distinguish between isolated warnings and findings that become significant when 
considered together. 
 
2.3.3 Results That Non-Experts Cannot Use 
 
Security scanners commonly produce technical findings containing rule identifiers, vulnerability classi-
fications, stack traces, source-code locations, or other information intended for experienced developers 
and security professionals. Such information can be useful for diagnosing a vulnerability but may not 
be sufficient for an application owner who created the system through natural-language prompting. A 
non-expert user needs to understand what the vulnerability means, what an attacker could potentially 
achieve, how serious the issue is, and what should be changed to reduce the risk. VibePen therefore 
treats the presentation of findings as an important part of the security-analysis process. Findings are 
intended to be normalized, validated against available evidence, assigned an appropriate severity, and 
converted into explanations using accessible language. Where appropriate, the report can also provide 
practical remediation guidance that helps the user understand the type of change required. This approach 
does not replace the underlying technical evidence; instead, it translates the evidence into a form that 
can support decision-making by users with different levels of security expertise. 
 
2.3.4 Authorized Testing 
 
Live application security testing introduces an ethical and operational requirement that must be ad-
dressed by the system. A scanner that allows any user to submit any website could potentially be 
used to probe applications without the owner’s permission. Such activity can expose sensitive infor-

mation, disrupt services, or create legal and ethical concerns. VibePen therefore restricts live scanning 
to applications for which the user has demonstrated ownership or authorization. The intended work-
flow begins with verification of domain control, after which the user can submit the authorized target for 
analysis. Dynamic checks are designed to use controlled and non-destructive requests rather than denial-
of-service, brute-force, or data-extraction techniques. During development and evaluation, the project 
team will use applications that it owns or is explicitly entitled to test, including applications developed 
by the team, open-source applications executed in controlled environments, and intentionally vulnerable 
training applications. Authorization is consequently treated as a core system requirement rather than an 
optional security feature. 
 
2.4 Goals and Objectives 
 
The primary goal of VibePen is to develop and evaluate a working vulnerability-scanning system specifi-
cally tailored to AI-generated web applications. The system should be capable of accepting both source-
code archives and authorized live applications, applying appropriate static and dynamic analysis tech-
niques, and presenting the resulting findings through a unified reporting mechanism. The project also 
aims to reduce the difficulty of interpreting security findings for non-expert users without removing the 
technical evidence required by developers and security testers. An AI-assisted reasoning layer will be 
used to validate findings, connect evidence across files and components, and reduce false positives while 
remaining constrained by available evidence. The objectives listed in Table 2.1 define measurable tar-
gets that can be used during project evaluation. These targets represent initial values and may be refined 
in consultation with the project supervisor as the implementation and evaluation methodology becomes 
more detailed. The objectives also establish clear boundaries for the system so that project progress can 
be evaluated against measurable outcomes rather than only against the completion of individual software 
features.

The scope of VibePen is to design and develop an automated security scanner for web applications 
produced through AI-assisted development. The project focuses on analyzing source-code archives 
and authorized live applications, identifying selected classes of security weaknesses, validating findings 
using available evidence, and presenting the results through prioritized and understandable reports. The 
project does not attempt to provide a complete replacement for professional penetration testing because 
comprehensive security assessment requires expertise, broader testing methodologies, and potentially 
longer assessment periods. The scope is instead limited to a defined set of vulnerability classes and

2.5.2 Out of Scope

3.1 Introduction 
 
This chapter reviews existing applications and research related to the security of web applications, with 
particular attention to projects created quickly through prompts and AI coding assistants. The review 
covers static application security testing, source-code parsing, secret detection, dependency analysis, dy-
namic testing, browser automation, and intentionally vulnerable applications used for evaluation. These 
systems solve different parts of the problem. Some inspect source code, some check dependencies 
against known vulnerability databases, and others test a running application. Their results are useful, 
but users may need technical experience to configure the tools and understand their output. Research 
on code generated by AI assistants also shows why security review is important: generated code can 
be functional while still containing security weaknesses [ 1]. The chapter therefore compares existing 
systems by their purpose, inputs, strengths, and limitations rather than assuming that one tool can iden-
tify every vulnerability. Product capabilities described here are based on the cited documentation and 
research. Since software tools change over time, their latest documentation should be checked again 
before the final submission. The review first discusses the available applications and test environments, 
then identifies the remaining gap and explains how VibePen is positioned in relation to them. 
 
3.2 Static Analysis and Source-Code Parsing 
 
Static application security testing (SAST) examines source code without running the application. It can 
identify suspicious patterns early in development and is useful when an AI-generated project is available 
as a folder or repository. Semgrep applies configurable rules to source code and supports custom rules for 
project-specific checks [4]. CodeQL represents code as a queryable database, allowing queries to trace 
data flow and find certain vulnerability patterns across functions [7]. SonarQube combines code-quality 
checks with security analysis and can be integrated into development workflows [8]. These tools provide 
complementary approaches: rule-based matching can be fast and easy to customize, while query-based 
analysis can express more complex relationships. However, their results still require interpretation. A 
match does not always prove that a vulnerability can be exploited, and a clean scan does not prove that 
an application is secure. Coverage also depends on supported languages, rules, configuration, and the 
information available to the scanner. VibePen can use these tools as evidence sources, but it should not 
present their findings as complete proof of security or treat the absence of findings as a guarantee. 
Source-code structure can help connect findings to the application in which they occur. Tree-sitter is 
a parser that builds syntax trees and is designed to work efficiently with source code, including code 
===== PAGE 27 =====
CHAPTER 3. RELATED APPLICATIONS 15 
 
that may be incomplete during editing [ 5]. It is not itself a vulnerability scanner; instead, its syntax 
information can help identify imports, function calls, routes, and other code structures. Bandit focuses 
on common security issues in Python code by examining its abstract syntax tree and applying security-
related plugins [9]. These projects illustrate two different roles: a parser provides structural information, 
while a security linter checks for selected patterns. Combining them can help a review system connect 
a finding to relevant code, but the combination still has limits. Parsing does not establish whether a 
route is reachable, and a rule-based warning may lack runtime context. For VibePen, source parsing is 
therefore treated as supporting evidence that helps organize code and guide analysis, rather than as an 
independent decision about whether a complete application is safe. 
 
3.3 Secret and Dependency Scanning 
 
Secret-scanning tools search source code and repositories for values that may be credentials, tokens, or 
other sensitive information. Gitleaks detects potential secrets in repositories and files using configured 
patterns and related heuristics [ 10]. This is important for generated projects because developers may 
accidentally include example credentials or copy values into source files. However, a secret scanner 
addresses a narrower problem than application security as a whole. A detected string may require ver-
ification, while credentials stored outside the scanned files may not be found. Dependency-scanning 
tools address a different risk: they identify libraries used by a project and compare them with records 
of known vulnerabilities. Snyk provides dependency and code-security capabilities documented for de-
velopment workflows [11]. OWASP Dependency-Check identifies project dependencies and checks for 
publicly disclosed vulnerabilities associated with them [ 12]. Trivy can scan software components and 
other supported targets for known vulnerabilities [ 13]. These tools are useful for finding known is-
sues in declared or detected components, but their coverage depends on accurate package identification 
and current vulnerability data. They do not automatically prove that a dependency is safe, nor do they 
necessarily establish whether a vulnerable component is reachable in the application. 
AI-generated projects also create a related package-integrity concern: a generated project may refer to a 
package name that is incorrect or does not correspond to the intended real package. Ordinary vulnerabil-
ity scanning is not sufficient for every such case because a scanner may only assess dependencies it can 
identify. A separate verification step can compare dependency declarations with the relevant package 
registry and project metadata. This check should report uncertainty when package identity cannot be es-
tablished, rather than labelling every unfamiliar name as malicious. The same cautious approach applies 
to secrets and dependency findings: each result should include the file, package, or evidence that caused 
it to be reported. The OWASP Top 10 describes broad categories of web application risk, including risks 
===== PAGE 28 =====
CHAPTER 3. RELATED APPLICATIONS 16 
 
related to vulnerable and outdated components, while the Common Weakness Enumeration provides a 
shared classification of software weaknesses [2, 3]. These references can help categorize findings con-
sistently. They are classification and guidance resources, however, not replacements for scanning or 
testing an actual application. 
 
3.4 Dynamic Analysis and Browser Automation 
 
Dynamic application security testing (DAST) tests a running application by sending requests and ob-
serving responses. OWASP ZAP provides an open-source proxy and scanning tools for web application 
testing [14]. Burp Suite offers a toolkit used for manual and automated web security testing [15]. Nuclei 
checks targets against templates for known vulnerabilities and configuration issues [16]. These applica-
tions can identify issues that are not obvious from source code alone, such as certain runtime behaviours 
or server responses. Their effectiveness depends on what they can reach and test. Authentication, appli-
cation state, rate limits, and crawling coverage may affect results, while active tests can create unwanted 
effects if they are run against systems without permission. The tools also produce findings that may need 
technical interpretation. A safe workflow should limit scans to authorized targets, prefer non-destructive 
checks where possible, and record enough evidence for a user to review a result. A scanner should not be 
run against a public site merely because its URL is available; permission and scope must be established 
first. 
Modern web applications may render much of their interface in the browser, so a simple HTTP crawler 
may not discover every page or action. Playwright automates browsers and can interact with web pages 
in a way similar to a user, making it useful for navigation and repeatable functional checks [6]. Browser 
automation can help a testing system discover reachable routes and collect responses, but it is not auto-
matically a security scanner. Its coverage depends on the actions, test accounts, and application states 
configured for a run. Dynamic analysis also benefits from an understanding of common security risks. 
The OWASP Server-Side Request Forgery Prevention Cheat Sheet, for example, provides guidance on 
reducing SSRF risks, which can inform checks and interpretation when relevant to the application ar-
chitecture [17]. Such guidance should be translated into bounded, safe tests rather than indiscriminately 
probing arbitrary systems. Together, proxy-based scanners, template scanners, and browser automation 
offer different forms of runtime evidence. A combined workflow can make use of each capability, pro-
vided that the system preserves the distinction between a detected pattern, a confirmed behaviour, and a 
vulnerability that has been validated in context.

3.5 AI-Assisted Security Analysis 
 
Large language models can help explain technical findings, summarize relevant source code, and suggest 
possible remediation steps. This may be helpful for users who do not have professional security expe-
rience. However, a model-generated explanation is not itself proof that a vulnerability exists. Models 
can misunderstand code, miss relevant context, or produce confident but incorrect statements. Research 
examining code generated by AI assistants has reported security weaknesses in generated snippets and 
has explored whether static-analysis feedback can help address some of those issues [1]. This supports 
the need for independent checks rather than relying only on an AI assistant’s own assessment. Another 
concern is prompt injection: source files, comments, web pages, or other content being analyzed may 
contain instructions intended to influence the model. Such content must be treated as untrusted data 
and must not override the system’s analysis instructions. A safer design gives the model bounded tasks, 
supplies findings from deterministic tools, and asks it to explain the available evidence. The model 
should be able to mark a result as uncertain or unsupported. This approach can improve readability 
while reducing the risk that a fluent explanation is mistaken for a verified security conclusion. 
 
3.6 Evaluation Applications and Test Environments 
 
A security system needs test applications whose relevant weaknesses are known or can be established 
independently. OWASP Juice Shop is an intentionally insecure web application designed for security 
training and demonstrations [18]. Damn Vulnerable Web Application (DVWA) provides a deliberately 
vulnerable environment for practicing common web security tests [ 19]. OWASP WebGoat is another 
educational application designed to teach web application security through lessons and exercises [ 20]. 
These projects are useful for controlled evaluation because they provide known examples of vulnerable 
behaviour. They should be deployed in a local or otherwise authorized environment and should not be 
treated as ordinary production sites. A separate test set can contain open-source projects that are re-
viewed offline for insecure patterns, exposed secrets, and vulnerable dependencies. The team can also 
build small applications from realistic prompts using AI coding tools, then inspect them and record the 
weaknesses that are deliberately included or independently confirmed. This provides examples closer to 
the target setting, although the generated applications must be documented carefully so that the evalua-
tion is reproducible. Test results should distinguish between vulnerabilities known to be present, findings 
reported by the system, missed issues, and incorrect findings. 
For each application, the evaluation should record the version or commit, configuration, test conditions, 
and the evidence used to establish the expected results. The same scope and test procedure should

be applied when comparing VibePen with individual tools, wherever their capabilities overlap. Suit-
able measures include recall, precision, and false-positive rate; these values should be calculated from 
recorded outcomes rather than estimated or invented. The test set should include more than one vulner-
ability category and more than one application so that results do not depend on a single example. If an 
application requires authentication, the test account and accessible features should be recorded without 
exposing real credentials. The PostgreSQL documentation on JSON types is relevant only if a compo-
nent of the proposed system stores or queries structured JSON data in PostgreSQL; it does not provide 
evidence about vulnerability detection itself [ 21]. More generally, documentation and benchmark de-
scriptions should be used only for claims they directly support. These evaluation practices help separate 
the capabilities of the existing applications from the proposed system’s own measured performance.

3.9 Positioning of VibePen 
 
VibePen is intended to sit between professional security tooling and people who create applications 
with AI coding assistants. The proposed workflow uses established scanners and source-analysis meth-
ods where they are suitable, then organizes the resulting evidence into findings that can be reviewed. 
Each finding should identify the relevant file, code location, dependency, request, or response when that 
evidence is available. The AI component should explain evidence and possible remediation rather than 
invent a vulnerability when the underlying tool output does not support it. The system should also distin-
guish confirmed findings from possible issues and indicate when a check could not be completed. These 
design choices are intended to make results more understandable without hiding uncertainty. VibePen 
is not intended to replace professional penetration testing, guarantee that an application is secure, or 
bypass the need for human review in high-impact situations. Its contribution will depend on the breadth 
of supported projects, the quality of its checks, the reliability of its explanations, and the results of its 
evaluation. 
 
3.10 Ethical and Legal Considerations 
 
Web security scanners can be configured to send requests to live services, so the system must establish 
authorization and scope before dynamic testing. A public URL is not, by itself, permission to scan 
a website. VibePen should require the user to confirm that they own the application or have explicit 
permission to test it, and it should limit scans to the approved host and scope. Rate limits, timeouts, 
non-destructive checks, and audit logs can reduce operational risk and make test activity traceable. The 
system should avoid actions that could modify data, disrupt service, or access information beyond the 
agreed scope. Where authorization cannot be established, the live scan should not proceed; code can 
instead be analyzed offline if the user is entitled to provide it. These controls are particularly important 
for a tool designed for non-expert users, who may not understand the effects of active scanning. The 
system should also handle submitted source code, secrets, and reports carefully, avoid exposing creden-
tials in generated output, and explain the limits of its findings. Ethical safeguards are part of the system 
requirements rather than optional additions to the scanner.

3.11 Conclusion 
 
This chapter reviewed static analysis, source parsing, secret detection, dependency scanning, dynamic 
testing, browser automation, AI-assisted review, and vulnerable applications used for evaluation. The 
reviewed projects provide established techniques for finding different kinds of issues, but no single tool 
guarantees complete security coverage. Research on AI-generated code further supports the need to test

is proposed as a guided workflow that combines evidence from existing tools, adds checks relevant to 
prompt-driven applications, and explains results in accessible language. Its value must be demonstrated

or prioritize those findings but must not create unsupported vulnerabilities. Users can review severity, 
location, redacted evidence, status, and recommended corrective steps. Administrators can manage users 
and rule configurations and inspect audit events. These features are intended to keep the process under-

4.9 Database Design 
 
VibePen uses a relational database because users, verified domains, scans, artifacts, findings, remedia-
tion records, and audit events have structured relationships that benefit from foreign keys and transac-
tional updates. PostgreSQL is a suitable candidate because its JSONB type can store redacted evidence 
whose shape varies between source-code excerpts and HTTP observations. Sensitive values should 
be minimized: passwords and verification tokens are represented by hashes, artifacts are identified by 
checksum and restricted storage path, and retained evidence is redacted before storage. The database 
schema does not replace application-level authorization or scan-scope checks; those controls must be 
enforced by the service layer. Figure 6.5 shows the proposed seven-entity model. 
 
4.9.1 Entity-relationship diagram 
 
As shown in Figure 6.5, a user can own multiple verified domains and scans and can generate audit 
events. A scan can reference a verified domain when it uses URL mode, while code mode may leave that 
reference empty. Each scan can contain multiple source artifacts and findings. Each finding is associated 
with one remediation record, allowing the explanation and corrective steps to be updated independently of 
the raw evidence. Foreign keys should prevent orphaned records, and application logic must reject URL 
scans whose verification has expired. The schema should be migrated and tested alongside the API to keep

Chapter 6  High-Level and Low-Level Design 
 
This chapter presents the high-level and low-level design of VibePen. The high-level design describes 
the system architecture, technology stack, modules, data flow, and deployment structure. The low-level 
design explains the database, user interfaces, API endpoints, class structure, and key algorithms. The 
chapter also discusses the security measures and design decisions used to make the system reliable, 
modular, and secure. 
 
6.1 System Overview 
 
VibePen is an AI-assisted security analysis system designed to identify potential security vulnerabilities 
in web applications. It combines static analysis, dynamic analysis, and AI-based reasoning to detect 
issues, validate findings, and generate reports with explanations and suggested fixes. 
The system supports two scanning modes. In code-based scanning, users upload a project archive for 
static analysis. In URL-based scanning, the system examines a live web application after verifying that 
the user is authorised to scan the target domain. 
VibePen follows a modular, service-oriented architecture. The frontend provides an interface for users to 
manage scans and view reports, while the backend handles authentication, validation, scan scheduling, 
analysis, and report generation. Separate workers perform static and dynamic analysis in isolated envi-
ronments. Their results are combined and processed by the AI reasoning module before being stored in 
the database. 
The main objectives of the design are to ensure that only authorised targets are scanned, reduce false-
positive findings, protect sensitive information, and provide understandable results to users. These ob-
jectives guide the architecture and the module boundaries described in the following sections. They also 
inform the decisions about data storage, scan isolation, evidence validation, and report generation. The 
design is intended to keep each stage understandable and independently testable, so that failures can be 
identified without losing all results from a scan. 
 
6.1.1 Design Principles 
 
The design of VibePen follows these principles: 
 
• Authorisation first: Scan live domains only after ownership verification. 
 
• Evidence-based analysis: AI explanations must be supported by tool evidence. 
 
• Isolation: Process archives and targets in controlled workers with resource limits. 
===== PAGE 56 =====
CHAPTER 6. HIGH-LEVEL AND LOW-LEVEL DESIGN 44 
 
• Modularity: Use common interfaces so analysis engines can be replaced independently. 
 
• Graceful degradation: Retain available findings and report incomplete checks after failures. 
 
• Data minimisation: Redact secrets and share only the context required for AI analysis. 
 
6.1.2 System Architecture 
 
VibePen uses a layered architecture in which the frontend communicates with a REST API. The API 
validates requests, checks permissions, and places scan jobs in a queue. Isolated workers execute the 
appropriate analysis engines. The resulting findings are normalised, processed by the AI reasoning 
module, assigned severity levels, and stored in the database. Finally, the report generator creates a 
structured report that users can access through the dashboard. 
The main layers of the system are summarised below. Figure 6.1 illustrates how the presentation, API, 
processing, AI reasoning, and data layers interact. 
• Presentation layer: Provides authentication, scan setup, progress, and reports. 
 
• API layer: Validates requests and handles authentication, permissions, and rate limits. 
 
• Processing layer: Schedules scans and runs isolated analysis workers. 
 
• AI reasoning layer: Validates findings and generates evidence-based explanations and fixes. 
 
• Data layer: Stores users, domains, scans, findings, remediation details, and audit logs.

6.1.4.1 Web Dashboard and API Gateway 
 
The web dashboard provides the user interface for account management, scan creation, scan progress, 
and report viewing. The API gateway receives requests from the frontend and validates them before 
processing. It also handles token-based authentication, per-user rate limits, and audit logging. It acts as 
the only component directly accessible from the internet. 
 
6.1.4.2 Ownership Verification Service and Scope Guard 
 
The ownership verification service confirms that a user is authorised to scan a live domain. It generates 
a random verification token and stores its hash with the associated user, domain, verification method, 
and expiry time. 
Users can verify a domain through one of three methods. The verification flow is shown in Figure 6.2. 
 
• Adding a TXT record at  vibepen-verify.<domain>. 
 
• Placing a verification file at /.well-known/vibepen-verify.txt. 
 
• Adding a verification meta tag to the website’s home page. 
 
A successful verification remains valid for 30 days. Subdomains are verified separately unless the parent 
domain is verified and the user explicitly chooses to include them. 
The Scope Guard controls outgoing requests made by the dynamic analysis engine. Before a request 
is sent, it checks whether the destination belongs to an authorised domain, resolves the hostname, and 
rejects private, loopback, or link-local IP addresses. Redirects are checked again before following them. 
These controls help prevent unauthorised scanning and server-side request forgery (SSRF), a risk ad-
dressed in the OWASP prevention guidance [17]. 
 
6.1.4.3 Static Analysis Engine 
 
The static analysis engine examines uploaded project archives without executing their code. It uses es-
tablished tools such as Semgrep and Tree-sitter for rule-based checks and source-code structure analysis 
[4, 5]. It operates inside a network-isolated container and consists of the following components: 
• Safe extractor: Enforces archive size, file-count, and path limits. 
 
• Rule scanner: Uses Semgrep and custom rules to detect secrets and common insecure code pat-
terns. 
• Code mapper: Uses Tree-sitter to map routes, middleware, calls, and database operations. 
 
• Dependency checker: Reviews manifests and flags missing, new, or look-alike package names.

6.1.4.4 Dynamic Analysis Engine 
 
The dynamic analysis engine uses Playwright to browse a live web application within configured page, 
depth, time, and request-rate limits [6]. All outgoing requests are controlled by the Scope Guard. 
The engine performs non-destructive checks, including: 
 
• Passive checks: Review headers, cookie flags, CORS, exposed paths, and response content. 
 
• Backend access checks: Use read-only requests to check access controls when a public client key 
is found. 
• Probe checks: Use harmless markers to identify reflected input and database errors. 
 
• IDOR checks: Optionally uses two test accounts supplied by the owner to check whether one 
account can access another account’s objects. 
The engine stops early if the target repeatedly returns server errors or times out. This helps reduce 
unnecessary requests and limits the impact on the target application. 
 
6.1.4.5 Finding Normalizer and AI Reasoning Module 
 
The finding normalizer converts results from different analysis engines into a common schema. Each 
finding contains its category, location, evidence, source engine, and initial severity. Duplicate findings 
are merged, and sensitive values are redacted before further processing. 
The AI reasoning module performs three main tasks: 
 
• Triage: Classifies findings and records confidence with supporting evidence. 
 
• Linking: Connects related routes, middleware, and database operations. 
 
• Explanation: Describes impact and recommends remediation in plain language. 
 
Several safeguards are applied to the AI reasoning process. Outputs must follow a JSON schema, and 
invalid outputs are retried once before being discarded. Evidence references are checked against the 
supplied context. The model cannot create findings without supporting tool evidence. Scanned content 
is treated as data, the model is not provided with tools or network access, and secret values are replaced 
with placeholders before external processing. If the model is unavailable, findings are retained and 
marked as unvalidated.

6.1.6 Deployment View 
 
VibePen is designed to run its main components in separate containers. The API, task queue, workers, 
and database are deployed independently so that their resources and responsibilities can be managed 
separately. 
Static and dynamic analysis workers use different container images. The static analysis worker has no 
outbound network access, while the dynamic analysis worker can send requests only through the Scope 
Guard. Uploaded archives and evidence are stored in an encrypted volume and removed according to 
the defined retention period. 
This deployment structure improves isolation, supports parallel processing, and reduces the risk that a failure 
in one component affects the entire system.

6.2.6.1 Scan Pipeline 
 
The scan orchestrator coordinates the complete analysis process. It checks authorisation where required, 
runs the applicable analyzers, processes their results, and generates the final report. 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
If an analyzer fails, the system records the failure and retains the results produced by the other analyzers. 
This supports partial reporting instead of losing all findings because of one failed component. 
 
6.2.6.2 Scope Verification Algorithm 
 
Before every outgoing request, the Scope Guard verifies that the destination is permitted. It checks the 
hostname against the verified hosts and rejects addresses that belong to private, loopback, or link-local 
ranges.
